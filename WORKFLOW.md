# Assignment 2: Prompting workflow comparison

Both implementations descend from baseline `059c8fa`, but they take different approaches. Round one (`fe02-vague`) replaces the dashboard in `src/App.tsx` with a standalone notification-settings page. Its `App` adds four alert types, email and in-app channels, delivery frequency, and quiet hours. Round two (`fe02-spec`) keeps the dashboard sections in `src/App.tsx`—including demo movie statistics, watchlist activity, popular movies, audience regions, and viewing suggestions—and renders a focused `NotificationSettings` component beneath them. This makes the second change narrower, while round one provides broader preference controls. The change to round one's page title and metadata in `index.html` also reflects its page replacement.

Accessibility exists in both versions. Round one's `App` labels navigation and the notification table, provides screen-reader labels for each channel checkbox and quiet-hours toggle, associates the frequency label with its select, labels both time inputs, and announces save status with `role="status"` and `aria-live="polite"`. Round two's `NotificationSettings` uses a visible “Email address” label, a labelled checkbox and save button, and polite live feedback. Its invalid-email path sets `aria-invalid`, links the error text through `aria-describedby`, and moves focus to the email input. Round one has no field-validation error to associate or focus; its status announces save success or failure.

The edge-case handling differs too. Round one's `isPreferences` checks the saved object’s fields and types; `loadPreferences` catches storage/JSON errors and falls back to defaults, logging the issue. It checks time values only as strings. Its `handleSubmit` reports storage write failure instead of marking it saved. Round two's `readPreferences` rejects malformed shapes and enabled notifications with an invalid email; read or parse exceptions produce a visible load error and defaults. `handleSubmit` trims email, validates it only when notifications are enabled, focuses invalid input, catches write failures, and shows success only after `setItem` succeeds. Its email check is a simple format regex, not full address verification.

Review and verification were not equivalent. Round one's diff adds no test file or test script, so its implementation has no automated feature coverage in that branch; review must inspect `App` and manually exercise settings and the replaced dashboard. Round two adds `src/components/NotificationSettings.test.tsx` with role-based tests for defaults, invalid and valid email, persistence, malformed JSON and invalid saved email, write failure, feedback clearing, and retained dashboard headings. The structured branch passed 11 tests and a production build on 2026-11-21 with Node.js 24.22.3 and npm 11.19.1. The vague branch's production build passed on the same runtime, but it has no test script. Review also caught an AI test-setup omission: `@testing-library/dom` was missing for the Testing Library queries; it is now a direct development dependency in `package.json`. The tests use Vitest-compatible assertions rather than relying on an unconfigured jest-dom matcher.

Exact durations were not recorded, so this is not a speed comparison. Round two required installation retries and review of test setup, behaviors, and results; that effort does not establish that it was faster or slower. ChatGPT guided the prompts, and GitHub Copilot implemented each round in a separate fresh chat.
